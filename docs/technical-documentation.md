## 1. Technologies Used

- **HTML5**: semantic structure (`header`, `main`, `section`, `nav`, `form`,
  `footer`), ARIA attributes for live regions and pressed states
- **CSS3**: custom properties (variables) for light/dark themes, Grid, Flexbox,
  `@keyframes` animations, transitions, `prefers-reduced-motion`
- **Vanilla JavaScript (ES6+)**: `const`/`let`, arrow functions, template
  literals, `Map`, destructuring, `IntersectionObserver`, `localStorage`
- No frameworks, no libraries, no build step, no backend. The script is a
  classic (non-module) script on purpose, so the site also works when
  `index.html` is opened directly from the file system.

3. **Projects (`#projects`)**:

The project cards are written directly in the HTML (not generated by

## 4. CSS Organisation (`css/styles.css`)

Top to bottom: variables (light + dark, now including `--error`), reset and
base, accessibility helpers, buttons, header, hero, **greeting**, about,
**filter controls**, **empty state**, project cards (with **tags** and hover
effects), contact form, footer, detail pages, **animations**, responsive rules.

Notes:

- `[hidden] { display: none !important; }` guarantees the `hidden` attribute
  always wins. Without it, a rule such as `display: flex` on a component would
  silently override it and the element would never hide.
- `.sr-only` visually hides the search label while keeping it available to
  screen readers.
- `:focus-visible` gives every interactive element a visible keyboard focus
  ring.
- `.projects-grid .folder-card { max-width: 520px; }` keeps a single remaining
  card from stretching across the whole row when the filter hides the other.

## 5. JavaScript Architecture (`js/script.js`)

The file is one IIFE with `"use strict"`. Each feature is its own function that
first looks up its elements and **returns immediately if any are missing**, so
the same file is safe on `index.html` and on both project pages.

```
initScrollReveal()  → fade/slide-in on scroll          (all pages)
initTheme()         → dark/light + localStorage         (all pages)
initSmoothScroll()  → smooth in-page anchor scrolling   (all pages)
initGreeting()      → time-of-day greeting + name       (index only)
initProjectFilter() → category filter + live search     (index only)
initContactForm()   → validation + success message      (index only)
```

Shared helpers:

- `storage.get / set / remove`: thin wrappers around `localStorage` with
  `try/catch`, because it can throw in private browsing or when site data is
  blocked. A failure never breaks the page.
- `replayAnimation(el, className)`: removes a class, forces a reflow
  (`void el.offsetWidth`) and adds it again so a CSS animation can run a second
  time.
- `prefersReducedMotion`: read once from `matchMedia`.

### 5.1 Scroll reveal

Elements with class `reveal` fade and slide up the first time they enter the
viewport.

1. An inline `<script>` in each page's `<head>` adds class `js` to `<html>`
   before the first paint.
2. CSS hides revealable elements only under that class:
   `.js .reveal:not(.is-visible) { opacity: 0; }`. If JavaScript is off, the
   class is never added and everything stays visible.
3. An `IntersectionObserver` (`threshold: 0.15`, bottom `rootMargin: -40px`)
   adds `is-visible` when an element scrolls in, then calls `unobserve`, so
   each element is revealed once and stops costing anything.
4. Children of any `[data-stagger]` container (the skill pills and the project
   grid) get an increasing `--reveal-delay` custom property (90 ms steps), so
   they arrive one after another.

**Design decision: animation, not transition.** The reveal is a `@keyframes`
animation with `animation-fill-mode: backwards`. After it finishes, the element
has *no* leftover `transform`, so the card's own `:hover { transform:
translateY(-8px) }` keeps working. An earlier idea (a transition to
`transform: none`) would have beaten the hover rule on specificity and killed
the hover lift.

**Fallbacks:** with no `IntersectionObserver`, or when the visitor prefers
reduced motion, every `.reveal` element gets `is-visible` immediately.

### 5.2 Theme toggle

Unchanged behaviour from Assignment 1: saved choice from `localStorage`,
otherwise the OS setting via `prefers-color-scheme`; clicking the button flips
`data-theme` on `<body>` and saves the new value (key `portfolio-theme`).

### 5.3 Smooth scrolling

`a[href^="#"]` links call `scrollIntoView`, using `behavior: "auto"` when the
visitor prefers reduced motion. `.section { scroll-margin-top: 24px; }` stops
the sticky header from covering the section label after a nav click on small
screens.

### 5.4 Personalised greeting

**Greeting word** (from the visitor's local clock, `new Date().getHours()`):

| Local time | Greeting |
|---|---|
| 05:00 – 11:59 | Good morning ☀️ |
| 12:00 – 16:59 | Good afternoon 🌤️ |
| 17:00 – 21:59 | Good evening 🌆 |
| 22:00 – 04:59 | Hello 🌙 |

The table lives in a `GREETINGS` array, so changing a time range or wording
means editing data, not logic.

**Name validation** (`validateName`): the input is trimmed and repeated spaces
are collapsed, then:

| Rule | Message shown |
|---|---|
| Not empty | "Please type your name first, then press “Say hi”." |
| At most 30 characters | "That name is a little long. Please use 30 characters or fewer." |
| Only letters (any language), spaces, hyphens, apostrophes | "Names can only contain letters, spaces, hyphens and apostrophes. Please remove any numbers or symbols and try again." |

The pattern is `/^[\p{L}\p{M}][\p{L}\p{M} '’-]*$/u`. Unicode property escapes
(`\p{L}`) are used instead of `[A-Za-z]` so that Arabic and other non-Latin
names are accepted. The input has `maxlength="40"` as a hard cap, while the
30-character rule gives a friendly message instead of silently cutting text.

**Flow:**

1. On load, `localStorage` is checked for `portfolio-visitor-name`. A stored
   value is **validated again**; if it is invalid (for example edited by hand
   in dev tools) it is deleted.
2. Valid saved name → greeting with the name, "Welcome back, nice to see you
   again.", and a *Not you?* button. No name → greeting word only plus the form.
3. Submitting a valid name saves it, shows "Nice to meet you!", plays a short
   pop-in animation and moves keyboard focus to the greeting. If the browser
   blocks storage, the message says so instead of failing silently.
4. *Not you?* removes the stored name, clears the field, shows the form again
   and focuses the input.

**Safety:** the name is inserted with `textContent` inside a `<bdi>` element,
never with `innerHTML`. Whatever is typed can only ever be text. `<bdi>` keeps
an Arabic name and the English greeting from scrambling each other's direction.

### 5.5 Project filter and live search

State is a small object: `{ category: "all", query: "" }`.

- **Search index:** built once at start-up. For each card, the title,
  description and tag text are joined, whitespace-normalised and lower-cased
  into a `Map` (card → string).
- **Matching** (`matches(card)`): a card is shown when
  1. the category is `all` or appears in the card's `data-category`, **and**
  2. *every* whitespace-separated word of the query appears somewhere in the
     card's text (case-insensitive, partial words allowed, so `fig` finds
     Figma).
- **`update()`** runs on every `input` event and every button click. It sets
  `card.hidden`, updates the result count, and shows or hides the empty state.
- **Entrance animation on re-show:** when a card goes from `display: none` back
  to visible, the browser restarts its CSS animation automatically, so no extra
  code is needed to animate cards back in.

| Situation | What the user sees | What to do next |
|---|---|---|
| Everything matches | "Showing 2 of 2 projects" | n/a |
| Some match | "Showing 1 of 2 projects" (announced via `aria-live`) | n/a |
| Nothing matches search | "No projects found: Nothing matches “zzz”. Check the spelling or try a different keyword." | Retype, or *Clear filters* |
| Nothing matches search + category | Message names both, e.g. “Nothing in UI/UX matches “hackathon”…” | *Clear filters* |
| Category has no projects | "There are no … projects yet. Pick another category…" | Choose another category |

*Clear filters* resets the search box and category, then returns focus to the
search box. The typed query is placed in the message with `textContent`, so
HTML typed into the search box is displayed as text.

## 6. Data Handling

| Key | Value | Written when | Read when |
|---|---|---|---|
| `portfolio-theme` | `"light"` or `"dark"` | Theme button clicked | Every page load |
| `portfolio-visitor-name` | Validated name string | Name form submitted | Index page load |

All data stays in the visitor's own browser. Nothing is sent anywhere.

## 7. Animations and Motion

| Where | Effect |
|---|---|
| Hero, section titles, About text, skills card, contact form | Fade and slide up on scroll |
| Skill pills, project cards | Same, staggered 90 ms apart |
| Project cards | Lift, image zoom, folder tab widens, tags take the card colour, "→" nudges right |
| Skill pills | Lift and tilt |
| Filter buttons, primary buttons | Lift (buttons also press down on `:active`) |
| Greeting, contact success, empty state | Pop-in |
| Name error | Short horizontal shake |
| Detail pages | Image and content blocks fade in on scroll |

All durations are short (0.2 – 0.7 s). With `prefers-reduced-motion: reduce`,
CSS turns off all animations and shortens transitions, and JavaScript skips the
observer and shows everything at once.

## 8. Accessibility

- Search input has a real `<label>` (visually hidden); the name input has a
  visible one.
- Filter buttons expose their state with `aria-pressed`.
- The result count is a polite live region; the name error is `role="alert"`
  and linked to its input with `aria-describedby` / `aria-invalid`.
- Focus is moved deliberately: to the greeting after saving a name, to the
  input after *Not you?*, to the search box after *Clear filters*.
- Visible `:focus-visible` outlines on all interactive elements.
- The active filter button is distinguished by background, border and weight,
  not by colour alone.
- Error colour changes in dark mode to keep contrast.

## 9. Responsive Design

Existing breakpoints (860 px, 600 px) are unchanged. Additions: the search box
and filter buttons wrap onto separate lines on narrow screens, the result count
moves to its own line at ≤ 600 px, and the greeting form wraps. No horizontal
scrolling was found at 375 px width.

## 12. Known Limitations and Ideas

- With only two projects, the filter is more of a demonstration than a
  necessity; it is built to scale (add a card with `data-category` and
  `.card-tags` and it is picked up automatically).
- The category buttons are written in HTML. If categories change, buttons and
  `data-category` values must be updated together.
- The name is stored per browser. There is no account or sync across devices.
- Search is simple substring matching: no typo tolerance or ranking.
